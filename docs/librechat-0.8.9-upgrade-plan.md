# Plan: Upgrade LibreChat from v0.8.8 to v0.8.9

**Status:** Planned, on branch `librechat-0.8.9`. Not yet implemented.
**Why:** v0.8.9 (released 2026-11-17, image `registry.librechat.ai/librechat-ai/librechat:v0.8.9`) adds `interface.theme`, a supported, validated deployment-wide theme. Our colors can move out of a custom stylesheet that depends on LibreChat internals, and into the generated `librechat.yaml`.
**Background:** [developer.md](../developer.md) (how the branding works today), [librechat-feasibility.md](librechat-feasibility.md).

The LibreChat theme documentation page still says the feature is "pending release"; that note is out of date. Everything below was checked against the source and built client inside the two official images, not only the docs.

---

## Goals

1. Run the demo on LibreChat v0.8.9, from its official, unmodified image (AGENTS.md §3).
2. Move the FDA colors into `interface.theme`, generated by `agent/librechat_config.py` like the rest of the configuration.
3. **Keep today's look.** This upgrade should show no visible change beyond LibreChat's own restyling. A redesign, if wanted, is a separate change (see [Not in this change](#not-in-this-change)).
4. Leave the agent itself unchanged: same prompt, skills, tools and spec.

### Two findings that shape the design

1. **Most of the hand-written chat-area CSS now has a token.** v0.8.9 names surfaces that v0.8.8 painted with shared or fixed colors:

   | Token (`rgb-` prefix) | Replaces in `theme.css` |
   |---|---|
   | `surface-sidebar` | sidebar via `surface-primary-alt` |
   | `surface-composer` | the message box via `surface-chat` |
   | `surface-user-message` | your own messages via a pale surface |
   | `surface-code-body`, `surface-code`, `syntax-*` | the `.markdown pre` rule |
   | `surface-code-inline` | the inline-`code` rule |
   | `table-header-fill`, `table-header-text` | the `.markdown th` rule |
   | `link-prose`, `prose-bullet`, `prose-quote-bar` | part of the `prose-invert` rule |
   | `field-fill`, `field-text` | possibly the `.webkit-dark-styles` rule (confirm on the login page) |
   | `button-primary`, `button-primary-hover` | buttons via `surface-submit` |

2. **There is no separate sidebar text color.** `rgb-text-primary` and friends are one value per mode for the whole app. White text on a navy sidebar next to dark text in a white chat area cannot be expressed with tokens alone, so a small scoped stylesheet stays.

   Related: the theme is applied as inline styles on `<html>` (`root.style.setProperty` in `packages/client/src/theme/utils/applyTheme.ts`). Inline styles beat any page-wide rule in `theme.css`, so that block must go. Rules on an inner element, such as `main:has(#prompt-textarea)`, still apply, because a variable set on an element beats the inherited one.

## Design (option 1: keep today's look)

- **`interface.theme`** carries the navy, white-text palette for the whole app: the page-wide block of today's `theme.css`, plus the new chat-only tokens (code body, inline code, table header, prose links, fields, user messages) set to their chat-area values. Those tokens are only used inside the chat area, so setting them globally is safe.
- The palette is one Python dict in `agent/librechat_config.py`, used for both `light` and `dark`, so the brand look stays the same in both modes, as today. High-contrast modes are untouched: LibreChat always gives them priority over the deployment theme.
- **`branding/theme.css`** shrinks to the `main:has(#prompt-textarea)` block: the text-color swap and the few surfaces that differ between the navy app and the white chat area (chat background, header bar, hover and active states, accent and focus ring). Keep the `prose-invert` rule only if dark-mode answers still need it.
- **`branding/apply.sh`** is unchanged: it still copies the logo, the icon and the (smaller) stylesheet.

## Changes

### Required

1. **`docker-compose.yml`:** pin `registry.librechat.ai/librechat-ai/librechat:v0.8.9`. Note the bump in the PR (AGENTS.md §7).
2. **`agent/librechat_config.py`:**
   - `CONFIG_VERSION = "1.3.19"`, with its comment updated.
   - Add the FDA palette and `interface.theme` (`version: 1`, `name`, `modes.light` and `modes.dark`). Values are quoted `"R G B"` strings; LibreChat rejects hex.
   - Set `interface.landingFooter` and `interface.messageAuthor` explicitly. v0.8.9 changes the defaults (`landingFooter: true` moves the footer to the bottom of the page; `messageAuthor: always`). Pick the values during the visual check, so a future default change can't alter the demo silently.
3. **`branding/theme.css`:** remove the page-wide block and the rules the new tokens replace (see the table above). Keep the scoped chat-area block. Update the header comment, which says "v0.8.8" and describes the file as the whole theme.
4. **`tests/test_librechat.py`:**
   - Offline: every theme color key starts with `rgb-` and every value is a valid `R G B` triplet (0–255). This catches the mistakes that make LibreChat drop the whole theme with only a log line.
   - Offline: light and dark use the same palette.
   - Live: LibreChat serves the generated theme in `/api/config` (it is pre-login configuration). This is the check that the theme was accepted rather than dropped. Confirm the exact response field during implementation.
   - `test_branding_files_are_where_apply_sh_copies_them` and `test_live_branding_is_the_branding_files` stay as they are.

### Docs to update along the way

- **`developer.md`:** rewrite "What is customized", "How it works" and "Change a color" around `interface.theme` plus the remaining scoped CSS. Fix two wrong claims: that v0.8.9 takes "the same variable names" (they gain an `rgb-` prefix and must be quoted), and that `theme.css` "can be dropped". Update the variable table to the token names. Add to "Upgrading LibreChat": check the LibreChat log for `Ignoring interface.theme` (whole theme dropped) and `names tokens this version ignores` (some tokens dropped).
- **`docs/librechat-feasibility.md`, `docs/librechat-migration-plan.md`:** these are design records. Add a short dated status note (v0.8.9 released 2026-11-17; colors now in `interface.theme`; see this plan) rather than rewriting them.
- **`README.md`:** check that the branding paragraph still holds. It probably needs no change.

## Verification

1. `docker compose exec jupyter pytest -m "not agent"` (includes the offline config tests).
2. `./start.sh`. It writes the new config, recreates LibreChat on the new image and restarts it. Then check the LibreChat log for theme warnings, MCP startup and skill loading.
3. Live tests: `docker compose exec jupyter pytest tests/test_librechat.py`.
4. Visual check from [developer.md, Checking a change](../developer.md#checking-a-change), in light, dark and both high-contrast modes:
   - the login page (logo, field text, button);
   - the new-chat screen (icon, starters, message box, footer position);
   - an answer with a table and a code block;
   - the `ask_user_question` form;
   - the model menu, account menu and Settings.

   Expect some spacing and corner-radius differences from LibreChat's own 0.8.9 restyling.
5. Short parity sample, which costs tokens: `EVAL_RUNTIME=librechat EVAL_RUNS=1 EVAL_QUESTIONS=<a few ids, including one ambiguous> pytest -m agent`. It confirms the chat stream and the paused-question handling are unchanged.
6. AWS: `./deploy/aws.sh up` after local checks pass, then `./deploy/aws.sh test`.

## Risks and rollback

- **MongoDB data migrates on first start**, including the MCP name-reservation index mentioned in the release notes. Going back to v0.8.8 on the same volume isn't guaranteed to work. Users and chats in this demo are disposable, so the rollback is:
  1. Revert the commit.
  2. Delete only the `mongodata` volume (not `pgdata`, so no `./stop.sh --reset`).
  3. Rerun `./start.sh`, which recreates the admin.
- **Background responses** need a transaction-capable MongoDB (a replica set). Ours is a standalone `mongod`. We don't use the feature, and spec `runInBackground` must stay off.
- **A rejected theme fails quietly.** LibreChat logs the problem and falls back to its default palette. The offline validity test and the live `/api/config` test exist for this.
- **The scoped CSS still depends on internals** (`#prompt-textarea`, `prose-invert`), but much less of it than before. Recheck it at each upgrade.

## Not in this change

- **A light interface with a navy sidebar** (option 2): white menus, dialogs and login page with dark text, and a tiny CSS rule for the sidebar text. It needs less CSS long term, but it is a visible redesign; do it separately if wanted.
- The bundled `clickhouse` theme, provider `brands` colors, and appearance settings (radii, fonts, shadows). Possible later; none is needed to keep today's look.
- Branded favicons and moving or reordering widgets (CSS can only hide or reorder within a container; see developer.md).
